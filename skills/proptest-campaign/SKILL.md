# Property-testing campaigns: staging and role-scoped specialization

For each selected module in a repository, identify a behavioral promise, build an independent executable check (`alpha: C -> A` or `RepInv`), and record what the check establishes—verified coverage across state transitions, resolved cross-module assumptions, unsettled specification questions, or minimal regressions. Treat campaign setup as **staging and partial evaluation (`discover_repo >>= (\repo_model -> specialize(workflow, repo_model))`)**: recover the repository's promises, caller obligations, ownership mode, and deliverable conventions once, write lean repo-specific sub-skills onto disk, and keep subagent contexts strictly role-scoped so each agent loads only the skill and equations its task requires.

Start the coordinator with **this skill alone** rather than loading every skill into one context window; read `write-reports` from the installed skills directory during Step 4 when specializing bucket reporting sub-skills (and `write-agent-prompts` only if authoring a custom domain-discovery sub-skill), and pass `proptest-praxis` by explicit file path only to module discovery workers.

## 1. Delegate initial reconnaissance to a Specification Scout

Keep the coordinator's context window lean by spawning a short-lived, read-only **Specification Scout** subagent (when subagents are available) to read repository docs and translate them into a source-cited contract summary before returning:

- **API promises, caller obligations, and staging rules:** inspect `README`, `CONTRIBUTING.md`, `SECURITY.md`, `AGENTS.md` / `CLAUDE.md`, public examples, and issue or PR templates. Return a structured map of (a) selected entry points, their accepted inputs, documented caller obligations, and promised behavior—citing the exact source (`doc`, `example`, `test`, or `code comment @ file:line`) for each claim rather than compressing hints into axioms—(b) test/DCO conventions and whether maintainers prefer minimal fix PRs vs. issue/reproduction-first discussion, and (c) staging rules from `CONTRIBUTING.md` / `SECURITY.md` when a finding arises, summarized strictly as contact path plus which `(entry_domain × violated_law)` combinations stay staged locally rather than becoming public branches or PRs.
- **Workspace architecture and compile loops:** inspect manifests (`Cargo.toml`, `package.json`, `*.gemspec`, `pyproject.toml`), CI configs, test runners (`cargo nextest`, `pytest`, `rake`), feature flags, and `unsafe` or C/FFI wrappers. Identify self-contained leaf crates (`1–3s` incremental builds) vs. heavy umbrella binaries where narrow pocket test binaries keep iteration fast, plus core data structures, planners, parsers, and composed `produce -> consume` pipelines where `produce(x)` must satisfy `consume`'s precondition.
- **Existing tests, uncertainty markers, and recent features:** sample existing property tests, grep for maintainer uncertainty comments (`TODO`, `FIXME`, `HACK`, `workaround`, `subtle`), and check `git log` for both recent bugfixes and **recently landed features/modes** whose interactions with older caches, visitors, and serializers lack generative coverage.

## 2. Interview the user on promises, ownership mode, and deliverables

Present a compact summary table of inferred repo defaults, then ask only the `2–4` unresolved questions whose answers change API obligations, repair philosophy, or deliverable packaging so the user can approve defaults in one reply or override specific rows. If the user asks to run unattended with defaults, record inferred assumptions explicitly as hypotheses and proceed.

Pin down four boundaries:

- **Accepted inputs, caller obligations, and promised behavior:** for each selected API, record the accepted input domain, documented caller obligations (e.g., plain script triggers a crash = runtime bug; C caller violates pointer precondition = caller error; regex engine on arbitrary strings vs. fixed developer literals), and specific promised laws (`Ok`/`Err` totality, `UNCHANGED` outside a workspace directory, safe-wrapper soundness, or explicit resource bounds only where promised). Cite the source for each law, mark inferred laws as hypotheses, and separate documented preconditions from incidental habits of current callers.
- **Ownership mode and repair scope ("what is worth fixing, and how deeply"):** whether this is an *external OSS contribution* (favoring minimal surgical diffs verified across sibling branches) or an *owned/internal repository* (where tightening representation types so `|Type| == |ValidStates|`, enforcing envelope bounds in a validated newtype at the boundary, and sweeping sibling call sites via `rg` are welcome), plus which behaviors sit outside the intended operating envelope. Ask which modules matter most and which are deprecated or off-limits.
- **Deliverable routing when a divergence surfaces (`Divergence -> Bucket_1 | ... | Bucket_k`):** when a check finds a discrepancy or unsettled contract, which disjoint destination applies—for example:
  1. *Correctness PR or internal root-fix PR* (minimal unit test + repair calibrated to ownership mode, verified across the generalized property suite and `--release`),
  2. *Design / tradeoff note* (reproduction-only unit test + option comparison when fixing alters public semantics, layout, or complexity tradeoffs),
  3. *Private maintainer report* (when `CONTRIBUTING.md`, `SECURITY.md`, or org norms designate a non-public maintainer path for a finding),
  4. *Outside-domain drop or local backlog* (logged in `ledger.md` without generating a report).
  Confirm whether outputs should stage locally for review before creating branches or tickets.
- **Compute budget:** parallel worktree count, `CARGO_BUILD_JOBS` cap, and availability of `Miri` or compiler sanitizers (`ASan`/`UBSan`).

## 3. Pin `target_sha`, set up `proptest/discovery`, and configure exclusions

Pin the campaign's upstream base commit `target_sha` (`git rev-parse HEAD` of `main`) once at setup so later discovery-branch commits never blur what unrepaired upstream code means. Create a local base branch (e.g., `proptest/discovery` off `target_sha`) and run parallel module investigations in dedicated `git worktree` checkouts on per-worker branches (`proptest/work-<module>` off `proptest/discovery`, since Git forbids checking out one branch in multiple worktrees), pruning finished worktree `target/` dirs or sharing `CARGO_TARGET_DIR` per build/sanitizer profile when disk or C `-sys` compile time matters.

Merge reusable verification code—reference models `A`, `alpha` projections, `RepInv` checks, narrow test binaries, `Arbitrary` strategies, and validated repairs that unmask deeper code paths (`advancing worker_base_sha`)—back into `proptest/discovery` so sibling worktrees can rebase cleanly, while keeping `target_sha` immutable as the delivery baseline. Append `.proptest-campaign/`, `proptest-regressions/`, `*.proptest-regressions`, and runner log globs to `$(git rev-parse --git-path info/exclude)` (which resolves the shared git exclude file across primary checkouts and linked worktrees where `.git` is a file) so local skills, notes, and regression seeds never dirty `git status` or commit history. Keep `.proptest-campaign/` anchored at `<primary-root>/.proptest-campaign/` and pass its absolute path when delegating to subagents.

## 4. Specialize `.proptest-campaign/` sub-skills on disk

Specialize [`write-reports`](../write-reports/SKILL.md) (if installed alongside this skill, or directly from the structure below) once to compile the repository's operating model into compact files under `<primary-root>/.proptest-campaign/`:

1. **`.proptest-campaign/operating-model.md` — Promises, Provenance, & Routing Table:**
   - Pinned `target_sha`, per-API table of accepted inputs, caller obligations, and promised laws with explicit source citations (`doc`, `example`, `test`, `comment @ file:line`, `user-confirmed`, or `hypothesis — verify`), ownership repair policy, and documented non-goals / drop rules.
   - Static routing table mapping `(entry_domain × violated_law × repair_clarity)` to each bucket when a minimal unit test over synthetic `"a"`/`"b"`/`TempDir` fixtures establishes a divergence.
   - Workspace recipes: fast leaf-crate / pocket-binary commands, OS write-confinement wrapper (`bwrap --ro-bind / / --bind "$temp" "$temp"`, `sandbox-exec`, or disposable container/VM) plus child-`Command` `TempDir` isolation for filesystem/archive/cleanup suites, `--release` parity checks, `Miri` (`PROPTEST_DISABLE_FAILURE_PERSISTENCE=1 PROPTEST_CASES=16`) and `ASan`/`UBSan` invocations, and `CARGO_BUILD_JOBS` limits.
2. **`.proptest-campaign/skills/<bucket-name>/SKILL.md` — Per-Channel Reporting Sub-Skills (for deliverable buckets 1–3):**
   - Write one self-contained `20–30` line skill per deliverable bucket so downstream writer agents need no other skill loaded, locking down: (a) exact `(entry_domain × violated_law × repair_clarity)` admission criteria (using concrete law names: `UNCHANGED` frame law, safe-wrapper soundness, AST spine invariance under leaf substitution, `alpha`/`RepInv` equivalence), (b) required repo verification commands—for repair buckets, verifying the test fails on its intended delivery base (`target_sha`, or `target_sha` plus declared `depends_on` repairs) and passes with the fix across the generalized property suite and `--release`; for reproduction-only tradeoff/ambiguity buckets, verifying the deterministic witness and contrastive baseline on `target_sha` (`or target_sha + depends_on`) without forcing a speculative patch—(c) repair depth and native repo test conventions, (d) strict diagnostic honesty (naming the tested API, citing any inspected caller that changes the conclusion, leaving uninspected callers marked `unverified`, and omitting speculative scenario prose), and (e) destination (`fix/<slug>` cut from `target_sha`—or stacked in `depends_on` order—vs. `.proptest-campaign/out/<bucket>/`).
3. **`.proptest-campaign/ledger.md` — Campaign State, Covered Transitions, & Discharged Obligations:**
   - Track pinned `target_sha`, modules modeled, worktrees, assigned laws checked (e.g., `alpha(step_impl(s, op)) == step_model(alpha(s), op)` for an exact state-machine model, or a one-sided cache/solution soundness relation, paired with `RepInv(s)`) with the exact operations covered and mutation-calibration status, **cross-module composition obligations** (`produce_fn`, `required_condition`, `consume_fn`, `resolution: open | "<function> establishes <condition> at <file:line> on <target_sha>" | violated_by(<test_name>)`), and divergences grouped into **root-cause equivalence classes** (`id`, `module`, `worker_base_sha`, `depends_on`, `repair_mode: patch | repro_only`, `violated_equation`, `caller_context: cited | unverified`, `test_name`, `status: candidate | verified | packaged | dropped`, `bucket`).

## 5. Role-scoped subagent orchestration and cross-module composition

Distribute work across lean, role-scoped contexts so every subagent saves tokens, starts with an uncontaminated `<thinking>` frame, and avoids sunk-cost bias. Because subagent harnesses do not auto-expand `$skill` sigils inside delegated prompts or scan `.proptest-campaign/skills/`, pass exact absolute `SKILL.md` file paths and instruct each subagent to read its assigned skill file first (when subagents or nested spawns are unavailable, execute these roles sequentially using `operating-model.md` and `ledger.md` as checkpoints):

1. **Specification Scout (`read-only`, runs once in Step 1):** digests raw repository docs, examples, manifests, and commit history into source-cited contract terms, then terminates.
2. **Coordinator (this context — `$proptest-campaign` + `operating-model.md` + `ledger.md`):** selects priority modules (`TODO`/`FIXME` hotspots, `Recent Feature × Older Consumer` pairs, coupled caches/planners), dispatches **Module Conformance Briefs**, sweeps sibling occurrences via `rg` when in owned-repo mode, orders or folds `depends_on` findings before packaging, and whenever Worker A reports an open cross-module assumption (*"`produce` omits `X`, assuming `consume` establishes `X`"*—or vice versa), dispatches a targeted composition check: for each supported input `x`, verify that `produce(x)` satisfies the documented precondition of `consume` and `consume(produce(x)) == expected(x)` (and, when a cited contract promises that a specific downstream observation `obs` ignores representation differences `x1 ~ x2`, check `obs(produce(x1)) == obs(produce(x2))`). Record whichever function establishes the condition—producer, intermediate adapter, or consumer—in `ledger.md` as `"<function> establishes <condition> at <file:line> on <target_sha>"` so the reuse scope for other callers stays explicit, or record the minimal `consume(produce(x))` counterexample when violated.
3. **Model & Harness Workers (read `proptest-praxis/SKILL.md` + a 10–15 line Module Conformance Brief only):** open every brief with an explicit verification assignment: *"Check whether `[named API]` satisfies `[behavioral promise]` over `[input domain]`. Evidence for that promise: `[doc, example, test, or labeled hypothesis @ file:line]`. Compare the implementation with `[independent model or soundness law]` at `[target_sha]`. Report what the comparison establishes, including the operations covered and any cross-module assumption left unresolved."* Pass fast test/sanitizer/OS-confinement commands while omitting governance docs and routing buckets. For verified clean modules, return the assigned law checked (such as `alpha(step_impl(s, op)) == step_model(alpha(s), op)` or a one-sided cache soundness relation, plus `RepInv(s)`), the exact operations covered, mutation-calibration confirmation, and any unresolved cross-module obligations. If a property failure or `Miri`/sanitizer diagnostic **directly establishes a violation of the assigned API promise** (with settled expected behavior), follow the regression workflow: replay the minimal test on `target_sha` (recording `depends_on` when an earlier discovery-branch repair on `worker_base_sha` unmasked it), rerun the law named in the brief over the recorded operations and `--release` before and after the candidate repair, and record the operations covered. If two defensible interpretations fit the docs, or if a failure/diagnostic's **relevance to the assigned API promise is unclear**, return `(target_sha, worker_base_sha, depends_on, file:line, observed counterexample or diagnostic, open question, unresolved cross-module obligations)` to the coordinator.
4. **Fresh-Eyes Reviewer (`read-only`, zero skills loaded — ideally on a second model family):** spawn a fresh source-level `read-only` agent (using a distinct model lineage when available so correlated blind spots don't grade their own homework) with *only* `target_sha`, `worker_base_sha`, `depends_on` (plus any prerequisite diff), the assigned law from the brief, the candidate test, captured delivery-base/`--release` output, covered-operations list, candidate diff or contract-option summary, module source at `target_sha`, and the **exact cited primary source (`doc/example/comment @ file:line`)** for the claimed promise rather than un-cited summaries. Read the cited primary text directly to check whether a competing interpretation fits; confirm that any repair-mode test genuinely fails before its fix on the intended delivery base rather than passing pre-fix on `target_sha` due to masking, that any candidate diff satisfies the assigned law from the brief (e.g., `alpha(step_impl(s, op)) == step_model(alpha(s), op)` for an exact state-machine model, or the brief's cache/partial-oracle soundness relation, plus `RepInv(s)`) over the recorded operations without regressing adjacent paths, and that the witness is minimal LOC. Name the API whose contract the test exercises; if an inspected caller changes the conclusion, cite it, and otherwise record caller behavior as `unverified`.
5. **Bucket Writer (reads *only* `<primary-root>/.proptest-campaign/skills/<bucket>/SKILL.md` + the verified test, `target_sha`/`depends_on` provenance, optional diff or option summary, and review note):** produces the clean `target_sha`-based branch (folding co-dependent repairs or stacking them in `depends_on` order so every branch's test fails pre-fix and passes post-fix) or the staged diagnostic/tradeoff writeup without exploratory search history in context.
