# Property-testing campaigns: staging and role-scoped specialization

For each selected module in a repository, identify its behavioral promises, build an independent executable check (`alpha: C -> A`, a forward-simulation / Blum checker relation, or `RepInv`), and record what the check establishes—verified coverage across state transitions, discharged **Rely–Guarantee** interface obligations, open specification questions, or minimal regressions. Treat campaign setup as **Futamura staging and partial evaluation (`discover_repo >>= (\repo_model -> specialize(workflow, repo_model))`)**: recover the repository's promises, caller obligations, ownership mode, and deliverable conventions once, compile lean repo-specific sub-skills onto disk, and hand each subagent the focused skill and inputs its role uses.

Begin the coordinator session with this skill and verify the companion skill paths up front (`../proptest-praxis/SKILL.md` for workers and `../write-reports/SKILL.md` for Step 4 unfolding, plus `../write-agent-prompts/SKILL.md` if authoring a custom domain sub-skill; if invoked from a standalone copy without sibling files, prompt for their paths or inline the model-verification rules directly).

## 1. Resolve `target_sha` and delegate reconnaissance to a Specification Scout

Resolve the user-requested target ref once at entry—defaulting to the current checkout `HEAD` (`target_sha = git rev-parse HEAD`)—before scouting, and use that recorded `target_sha` everywhere afterward. Spawn a short-lived, read-only **Specification Scout** subagent (when subagents are available) reading a view pinned at `target_sha` (such as a detached worktree at `target_sha` or `git show <target_sha>:<path>`) so every contract, example, and `file:line` citation matches the exact revision under test:

- **API promises, caller obligations, and deliverable conventions:** inspect `README`, `CONTRIBUTING.md`, `SECURITY.md`, `AGENTS.md` / `CLAUDE.md`, public examples, and issue or PR templates at `target_sha`. Return a structured map of (a) selected entry points, their accepted inputs, documented caller obligations, and promised behavior—preserving the exact source (`doc`, `example`, `test`, or `code comment @ file:line` on `target_sha`) for each claim—(b) test/DCO conventions, whether the repository commits `proptest-regressions/` seeds, and minimal-patch vs. discussion-first norms, and (c) repository deliverable paths from `CONTRIBUTING.md` / `SECURITY.md` (`contact route plus which (entry_domain × violated_law) combinations stage locally under .proptest-campaign/out/`).
- **Workspace architecture and compile loops:** inspect manifests (`Cargo.toml`, `package.json`, `*.gemspec`, `pyproject.toml`), CI configs, test runners (`cargo nextest`, `pytest`, `rake`), feature flags, and `unsafe` or C/FFI wrappers at `target_sha`. Identify self-contained leaf crates (`1–3s` incremental builds) vs. heavy umbrella binaries where narrow pocket test binaries keep iteration fast, plus core data structures, planners, parsers, and composed `produce -> consume` pipelines where `produce(x)` must satisfy `consume`'s precondition.
- **Existing tests, uncertainty markers, fix neighborhoods, and recent features:** sample existing property tests, grep for maintainer uncertainty comments (`TODO`, `FIXME`, `HACK`, `workaround`, `subtle`), and check `git log <target_sha>` for **recent bugfix, bounds-check, and security-relevant commits** (which frequently carry adjacent correctness impacts—updating one side of a coupled invariant or guarding a single call site while leaving sibling paths inconsistent) alongside **recently landed features/modes** whose interactions with older caches, visitors, and serializers lack generative coverage.

## 2. Interview the user on promises, ownership mode, and deliverables

Present a compact summary table of inferred repo defaults at `target_sha`, then filter by **value of information (`VoI`)**: ask only the `2–4` unresolved questions whose answers branch API obligations, repair philosophy, or deliverable packaging so the user can approve defaults in one reply or override specific rows. If the user asks to run unattended with defaults, record inferred assumptions explicitly as hypotheses and proceed.

Pin down four boundaries:

- **Accepted inputs, caller obligations, and promised behavior:** for each selected API, record the accepted input domain, documented caller obligations (e.g., plain script triggers a crash = runtime bug; C caller violates pointer precondition = caller error; regex engine on arbitrary strings vs. fixed developer literals), and specific promised laws (`Ok`/`Err` totality, `UNCHANGED` outside a workspace directory, safe-wrapper soundness, or explicit resource bounds only where promised). Cite the source for each law, mark inferred laws as hypotheses, and separate documented preconditions from incidental habits of current callers.
- **Ownership mode and repair scope ("what is worth fixing, and how deeply"):** whether this is an *external OSS contribution* (favoring minimal surgical diffs verified across sibling branches) or an *owned/internal repository* (where tightening representation types so `|Type| == |ValidStates|`, enforcing envelope bounds in a validated newtype at the boundary, and sweeping sibling call sites via `rg` are welcome), plus the user's authority (`api-owner` vs. `downstream-caller`) for each target API and which modules are priority vs. deprecated.
- **Deliverable routing when a divergence surfaces (`Divergence -> Bucket_1 | ... | Bucket_k`):** when a check finds a discrepancy or unsettled contract, which disjoint destination applies—for example:
  1. *Correctness PR or internal root-fix PR* (minimal unit test + repair calibrated to ownership mode, verified on the exact delivery branch as well as the property suite and `--release`),
  2. *Design / tradeoff note* (reproduction-only unit test + option comparison when fixing alters public semantics, layout, or complexity tradeoffs),
  3. *Private maintainer report* (when `CONTRIBUTING.md`, `SECURITY.md`, or org norms designate a non-public maintainer path for a finding),
  4. *Outside-domain drop or local backlog* (logged in `ledger.md` without generating a report).
  Confirm whether outputs should stage locally for review before creating branches or tickets.
- **Compute budget:** parallel worktree count, `CARGO_BUILD_JOBS` cap, and availability of `Miri`, compiler sanitizers (`ASan`/`UBSan`), and OS write-confinement wrappers (`bwrap` / `sandbox-exec` / container).

## 3. Set up `proptest/discovery` off `target_sha` and manage reversible exclusions

Create a local base branch (`proptest/discovery` off the `target_sha` pinned in Step 1) and run parallel module investigations in dedicated `git worktree` checkouts on per-worker branches (`proptest/work-<module>` off `proptest/discovery`, since Git forbids checking out one branch in multiple worktrees), pruning finished worktree `target/` dirs or sharing `CARGO_TARGET_DIR` per build/sanitizer profile when disk or C `-sys` compile time matters.

Merge reusable verification code—reference models `A`, `alpha` projections, `RepInv` checks, narrow test binaries, `Arbitrary` strategies, and validated repairs that unmask deeper code paths (`advancing worker_base_sha`)—back into `proptest/discovery` so sibling worktrees can rebase cleanly, keeping `target_sha` immutable as the delivery baseline. Anchor campaign files and runner logs under `<primary-root>/.proptest-campaign/` (passing its absolute path to subagents). Honor the repository's seed policy: add `.proptest-campaign/` (plus `proptest-regressions/` and `*.proptest-regressions` only when `git ls-files 'proptest-regressions*'` and `.gitignore` show the project does not track seeds) inside a `# begin/end proptest-campaign` block in `$(git rev-parse --git-path info/exclude)`, and have the coordinator remove that block when the campaign ends so ordinary development retains its normal `git status` behavior.

## 4. Unfold `.proptest-campaign/` sub-skills onto disk

Specialize [`write-reports`](../write-reports/SKILL.md) (if installed alongside this skill, or directly from the structure below) once to unfold the repository's operating model into compact files under `<primary-root>/.proptest-campaign/`:

1. **`.proptest-campaign/operating-model.md` — Promises, Provenance, & Routing Table:**
   - Pinned `target_sha` (and target ref name), per-API table of accepted inputs, caller obligations, and promised laws with explicit provenance (`doc`, `example`, `test`, or `comment @ file:line` on `target_sha`; verbatim Step-2 decision records tagged by speaker authority **for that specific API** as `api-owner-confirmed (<id>: "<verbatim quote>")` vs. `caller-expectation (<id>: "<verbatim quote>")`; or `hypothesis — verify`), ownership repair policy, seed-tracking policy, and documented non-goals.
   - Static routing table mapping `(entry_domain × violated_law × repair_clarity)` to each bucket when a minimal unit test over synthetic `"a"`/`"b"`/`TempDir` fixtures establishes a divergence.
   - Workspace recipes: fast leaf-crate / pocket-binary commands, conditional checks (`--release` parity, `Miri` with `PROPTEST_DISABLE_FAILURE_PERSISTENCE=1 PROPTEST_CASES=16` for `unsafe`/`Pin`, `ASan`/`UBSan` for C/FFI, and `bwrap`/container confinement with nested writable ancestor sentinels when generated paths reach mutating filesystem calls), and `CARGO_BUILD_JOBS` limits. When several target modules share one core IR, schema, or AST (such as multiple planner passes or codec stages), also unfold a compact `.proptest-campaign/domain-fixtures.md` (using `write-agent-prompts` if loaded) capturing the shared miniature valid-AST generator, planted-solution recipe, and in-repo McKeeman differential pairs once so workers reuse them directly.
2. **`.proptest-campaign/skills/<bucket-name>/SKILL.md` — Unfolded Reporting Sub-Skills (for deliverable buckets 1–3):**
   - Compile one self-contained `20–30` line skill per deliverable bucket so each writer starts from a tailored guide: (a) `(entry_domain × violated_law × repair_clarity)` criteria (using concrete law names: `UNCHANGED` frame law, safe-wrapper soundness, AST spine invariance under leaf substitution, `alpha`/`RepInv` equivalence), (b) delivery-tree verification commands—for repair buckets, replaying the native regression test on the exact **delivery parent SHA** (`pre-fix fail`) and **delivery tip SHA** (`post-fix pass` plus `--release`), recording both SHAs alongside `worker_base_sha`; for reproduction-only tradeoff/ambiguity buckets, replaying the deterministic witness and contrastive baseline on the delivery base (`target_sha` or `target_sha + depends_on`) alongside candidate contract options—(c) repair depth and native repo test conventions, (d) witness-led precision (naming the tested API, treating `api-owner-confirmed` decisions as intended API behavior while framing `caller-expectation` items where docs are silent as specification questions or caller integration tests, citing any inspected caller that changes the conclusion, and marking uninspected callers `unverified`), and (e) destination (`fix/<slug>` cut from `target_sha`—or stacked in `depends_on` order—vs. `.proptest-campaign/out/<bucket>/`).
3. **`.proptest-campaign/ledger.md` — Campaign State, Covered Transitions, & Discharged Obligations:**
   - Track pinned `target_sha`, modules modeled, worktrees, laws checked (`law_checked`, tested domain, exact `ops_covered`, `case_count`, and calibration result, or `inconclusive` reason), **cross-module composition obligations** (`produce_fn`, `required_condition`, `consume_fn`, `resolution: open | "<function> establishes <condition> at <file:line> on <target_sha>" (reserved for source-level or exhaustive proofs) | "sampled <N> cases (<domain>) on <target_sha>: 0 violations" | violated_by(<test_name>)`), and divergences grouped into **root-cause equivalence classes** (`id`, `module`, `worker_base_sha`, `delivery_parent_sha`, `delivery_tip_sha`, `depends_on`, `repair_mode: patch | repro_only`, `law_checked`, `caller_context: cited | unverified`, `test_name`, `status: candidate | verified | packaged | inconclusive | dropped`, `bucket`).

## 5. Role-scoped subagent orchestration and cross-module composition

Give each subagent a crisp, focused brief and the single skill file its role uses so every context starts fresh and unencumbered by prior search history. Because subagent harnesses do not auto-expand `$skill` sigils inside delegated prompts or scan `.proptest-campaign/skills/`, pass exact absolute `SKILL.md` file paths and ask each subagent to read its assigned skill file first (when running in a single context, walk these roles sequentially using `operating-model.md` and `ledger.md` as state):

1. **Specification Scout (`read-only`, runs once in Step 1 on `target_sha`):** digests repository docs, examples, manifests, and commit history at `target_sha` into source-cited contract terms, then returns.
2. **Coordinator (this context — `$proptest-campaign` + `operating-model.md` + `ledger.md`):** selects high-leverage modules (`TODO`/`FIXME` hotspots, neighborhoods around recent bugfix/security-relevant commits, `Recent Feature × Older Consumer` pairs, coupled caches/planners), dispatches **Module Conformance Briefs** (passing `.proptest-campaign/domain-fixtures.md` when unfolded), sweeps sibling occurrences via `rg` in owned-repo mode, orders or folds `depends_on` findings before packaging, and turns worker assumptions and incidental observations into follow-up checks. Whenever Worker A records an open `produce -> consume` assumption, dispatch a composition check across supported inputs `x`: verify that `produce(x)` satisfies `consume`'s documented precondition and fulfills the promised relation between `x` and `consume(produce(x))` (such as `consume(produce(x)) == expected(x)` when unique, or solution-validity predicates like topological order when multiple outputs satisfy the contract; plus `obs(produce(x1)) == obs(produce(x2))` where `obs` promises representation-insensitivity), recording a source-level `"<function> establishes <condition> at <file:line> on <target_sha>"` or finite-sample `"sampled <N> cases..."` entry in `ledger.md`, or capturing the minimal `consume(produce(x))` counterexample. Whenever an observation falls outside a worker's assigned law, check whether a separately supported promise explains its relevance and issue a new brief for that promise; remove the `# begin/end proptest-campaign` block from `info/exclude` when the campaign concludes.
3. **Model & Harness Workers (given `proptest-praxis/SKILL.md` + a concise `Module Conformance Brief`):** dispatch each worker with a structured brief separating the fast discovery loop from conditional checks so pure in-memory suites run immediately without waiting on specialized tools:

   ```yaml
   target_sha: "<pinned sha>"
   module: "<path and named API(s)>"
   promises: "<laws to check + citation @ file:line | api-owner-confirmed(id: 'verbatim quote') | caller-expectation(id: 'verbatim quote') | hypothesis>"
   model_law: "<alpha(step_impl(s, op)) == step_model(alpha(s), op) | cache/solution soundness relation + RepInv>"
   preconditions: "<documented caller/unsafe obligations to uphold>"
   fast_check: "<1-3s cargo/pytest target command>"
   conditional_checks: "<--release on candidate divergences; Miri when unsafe/Pin present; ASan/UBSan when C/FFI present; bwrap/container + nested writable ancestor sentinels when generated paths reach mutating filesystem calls>"
   ```

   While the worktree and build cache are warm, workers can immediately add checks for adjacent promises on the same module that code reading or testing brings into focus (such as multiset preservation alongside sort order) whenever repo evidence supports them. Workers return one structured `Worker Outcome` per module or root-cause class—setting `law_checked` and `promise_source` to the exact law and evidence that exposed a finding, or `status: "inconclusive"` when a calibration mutation goes undetected, target transitions go unreached, or a required conditional tool is unavailable:

   ```yaml
   status: "verified_clean | confirmed_divergence | open_question | inconclusive"
   provenance: { target_sha: "<sha>", worker_base_sha: "<sha>", depends_on: ["<id>"], api: "<fn>", promise_source: "<file:line | tagged verbatim quote>" }
   coverage: { law_checked: "<law>", domain: "<inputs>", ops_covered: ["<op>"], case_count: "<N>", calibration_break_caught: "<mutation & step | missed_reason>" }
   witness: "<minimal #[test] or observed diagnostic + command & delivery-base/--release output>"
   resolution: "<verified candidate diff | candidate contract options | open question | inconclusive reason>"
   leads: ["<produce -> consume assumption or adjacent promise to check next>"]
   ```

   When a failure or `Miri`/sanitizer diagnostic directly establishes a violation of a settled module promise, workers replay the minimal test on `target_sha` (recording `depends_on` when unmasked by an earlier `worker_base_sha` repair) and rerun `law_checked` (alongside the brief's `model_law` as a regression guard) over `ops_covered` and `--release` before and after the candidate repair; when two defensible interpretations fit the docs or an observation points outside supported module promises, workers return `status: "open_question"` with the observed witness and `leads` for the coordinator.
4. **Fresh-Eyes Reviewer (`read-only`, N-version decorrelated check — ideally on a second model family):** hand a fresh source-level `read-only` agent (using a distinct model lineage when available to decorrelate shared family blind spots) a self-contained review packet: `target_sha`, `worker_base_sha`, `depends_on` (plus any prerequisite diff), `law_checked` (and the original `model_law` when distinct), candidate test, captured delivery-base/`--release` output, `ops_covered`, candidate diff or contract-option summary, module source at `target_sha`, and `promise_source` carrying either the cited repository location (`doc/example/comment @ file:line`) or the inline `api-owner-confirmed` / `caller-expectation` verbatim quote. Read repository citations directly to test whether a competing interpretation fits, and distinguish an `api-owner-confirmed` API decision from a downstream `caller-expectation` (even inside an owned monorepo) when docs are silent; confirm repair-mode tests fail pre-fix on their intended delivery base, satisfy `law_checked` (and `model_law`) over `ops_covered` post-fix, and keep the witness minimal in LOC. Name the tested API, citing any inspected caller that changes the conclusion and marking uninspected callers `unverified`.
5. **Bucket Writer (given `<primary-root>/.proptest-campaign/skills/<bucket>/SKILL.md` + the verified review packet):** cuts the clean `target_sha`-based delivery branch (folding co-dependent repairs or stacking them in `depends_on` order), executes the native regression test on the exact **delivery parent SHA** (`confirming expected pre-fix failure`) and **delivery tip SHA** (`confirming post-fix pass` plus `--release`), and records `delivery_parent_sha`, `delivery_tip_sha`, `worker_base_sha` (the discovery harness revision for reconstructing the full property run), runnable command, and results in the branch or staged writeup.
