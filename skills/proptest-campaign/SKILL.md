# Property-testing campaigns: staging and role-scoped specialization

For each selected module in a repository, identify its behavioral promises, build an independent executable check (`alpha: C -> A`, a soundness relation, or `RepInv`), and record what the check establishes—verified coverage across state transitions, discharged cross-module assumptions, open specification questions, or minimal regressions. Treat campaign setup as **staging and partial evaluation (`discover_repo >>= (\repo_model -> specialize(workflow, repo_model))`)**: recover the repository's promises, caller obligations, ownership mode, and deliverable conventions once, compile lean repo-specific sub-skills onto disk, and hand each subagent the focused skill and inputs its role uses.

Begin the coordinator session with this skill; read `write-reports` from the installed skills directory during Step 4 when unfolding bucket reporting sub-skills (and `write-agent-prompts` when authoring a custom domain-discovery sub-skill), and pass `proptest-praxis` by file path to module discovery workers.

## 1. Delegate initial reconnaissance to a Specification Scout

Keep the coordinator's context window lean by spawning a short-lived, read-only **Specification Scout** subagent (when subagents are available) to read repository docs and return a source-cited contract summary:

- **API promises, caller obligations, and deliverable conventions:** inspect `README`, `CONTRIBUTING.md`, `SECURITY.md`, `AGENTS.md` / `CLAUDE.md`, public examples, and issue or PR templates. Return a structured map of (a) selected entry points, their accepted inputs, documented caller obligations, and promised behavior—preserving the exact source (`doc`, `example`, `test`, or `code comment @ file:line`) for each claim—(b) test/DCO conventions and minimal-patch vs. discussion-first norms, and (c) repository deliverable paths from `CONTRIBUTING.md` / `SECURITY.md` (`contact route plus which (entry_domain × violated_law) combinations stage locally under .proptest-campaign/out/`).
- **Workspace architecture and compile loops:** inspect manifests (`Cargo.toml`, `package.json`, `*.gemspec`, `pyproject.toml`), CI configs, test runners (`cargo nextest`, `pytest`, `rake`), feature flags, and `unsafe` or C/FFI wrappers. Identify self-contained leaf crates (`1–3s` incremental builds) vs. heavy umbrella binaries where narrow pocket test binaries keep iteration fast, plus core data structures, planners, parsers, and composed `produce -> consume` pipelines where `produce(x)` must satisfy `consume`'s precondition.
- **Existing tests, uncertainty markers, and recent features:** sample existing property tests, grep for maintainer uncertainty comments (`TODO`, `FIXME`, `HACK`, `workaround`, `subtle`), and check `git log` for both recent bugfixes and **recently landed features/modes** whose interactions with older caches, visitors, and serializers lack generative coverage.

## 2. Interview the user on promises, ownership mode, and deliverables

Present a compact summary table of inferred repo defaults, then ask only the `2–4` unresolved questions whose answers change API obligations, repair philosophy, or deliverable packaging so the user can approve defaults in one reply or override specific rows. If the user asks to run unattended with defaults, record inferred assumptions explicitly as hypotheses and proceed.

Pin down four boundaries:

- **Accepted inputs, caller obligations, and promised behavior:** for each selected API, record the accepted input domain, documented caller obligations (e.g., plain script triggers a crash = runtime bug; C caller violates pointer precondition = caller error; regex engine on arbitrary strings vs. fixed developer literals), and specific promised laws (`Ok`/`Err` totality, `UNCHANGED` outside a workspace directory, safe-wrapper soundness, or explicit resource bounds only where promised). Cite the source for each law, mark inferred laws as hypotheses, and separate documented preconditions from incidental habits of current callers.
- **Ownership mode and repair scope ("what is worth fixing, and how deeply"):** whether this is an *external OSS contribution* (favoring minimal surgical diffs verified across sibling branches) or an *owned/internal repository* (where tightening representation types so `|Type| == |ValidStates|`, enforcing envelope bounds in a validated newtype at the boundary, and sweeping sibling call sites via `rg` are welcome), plus which behaviors sit outside the intended operating envelope. Ask which modules matter most and which are deprecated or off-limits.
- **Deliverable routing when a divergence surfaces (`Divergence -> Bucket_1 | ... | Bucket_k`):** when a check finds a discrepancy or unsettled contract, which disjoint destination applies—for example:
  1. *Correctness PR or internal root-fix PR* (minimal unit test + repair calibrated to ownership mode, verified across the generalized property suite and `--release`),
  2. *Design / tradeoff note* (reproduction-only unit test + option comparison when fixing alters public semantics, layout, or complexity tradeoffs),
  3. *Private maintainer report* (when `CONTRIBUTING.md`, `SECURITY.md`, or org norms designate a non-public maintainer path for a finding),
  4. *Outside-domain drop or local backlog* (logged in `ledger.md` without generating a report).
  Confirm whether outputs should stage locally for review before creating branches or tickets.
- **Compute budget:** parallel worktree count, `CARGO_BUILD_JOBS` cap, and availability of `Miri` or compiler sanitizers (`ASan`/`UBSan`).

## 3. Pin `target_sha`, set up `proptest/discovery`, and configure exclusions

Resolve the user-requested target ref once at entry—defaulting to the current checkout `HEAD` (`target_sha = git rev-parse HEAD`, rather than hardcoding `main` when the user is testing a feature branch)—and use that recorded `target_sha` everywhere afterward so later discovery-branch commits never blur the baseline revision. Create a local base branch (e.g., `proptest/discovery` off `target_sha`) and run parallel module investigations in dedicated `git worktree` checkouts on per-worker branches (`proptest/work-<module>` off `proptest/discovery`, since Git forbids checking out one branch in multiple worktrees), pruning finished worktree `target/` dirs or sharing `CARGO_TARGET_DIR` per build/sanitizer profile when disk or C `-sys` compile time matters.

Merge reusable verification code—reference models `A`, `alpha` projections, `RepInv` checks, narrow test binaries, `Arbitrary` strategies, and validated repairs that unmask deeper code paths (`advancing worker_base_sha`)—back into `proptest/discovery` so sibling worktrees can rebase cleanly, while keeping `target_sha` immutable as the delivery baseline. Append `.proptest-campaign/`, `proptest-regressions/`, `*.proptest-regressions`, and runner log globs to `$(git rev-parse --git-path info/exclude)` (which resolves the shared git exclude file across primary checkouts and linked worktrees where `.git` is a file) so local skills, notes, and regression seeds never dirty `git status` or commit history. Keep `.proptest-campaign/` anchored at `<primary-root>/.proptest-campaign/` and pass its absolute path when delegating to subagents.

## 4. Unfold `.proptest-campaign/` sub-skills onto disk

Specialize [`write-reports`](../write-reports/SKILL.md) (if installed alongside this skill, or directly from the structure below) once to unfold the repository's operating model into compact files under `<primary-root>/.proptest-campaign/`:

1. **`.proptest-campaign/operating-model.md` — Promises, Provenance, & Routing Table:**
   - Pinned `target_sha` (and target ref name), speaker role (`maintainer` in owned repos vs. `external-caller` in external OSS contributions), per-API table of accepted inputs, caller obligations, and promised laws with explicit provenance (`doc`, `example`, `test`, or `comment @ file:line`; verbatim Step-2 decision records tagged by speaker role as `maintainer-confirmed (<decision-id>: "<answer>")` or `caller-expectation (<decision-id>: "<answer>")`; or `hypothesis — verify`), ownership repair policy, and documented non-goals.
   - Static routing table mapping `(entry_domain × violated_law × repair_clarity)` to each bucket when a minimal unit test over synthetic `"a"`/`"b"`/`TempDir` fixtures establishes a divergence.
   - Workspace recipes: fast leaf-crate / pocket-binary commands, OS write-confinement wrapper (`bwrap --ro-bind / / --bind "$temp" "$temp"`, `sandbox-exec`, or disposable container/VM) plus child-`Command` `TempDir` isolation for filesystem/archive/cleanup suites, `--release` parity checks, `Miri` (`PROPTEST_DISABLE_FAILURE_PERSISTENCE=1 PROPTEST_CASES=16`) and `ASan`/`UBSan` invocations, and `CARGO_BUILD_JOBS` limits.
2. **`.proptest-campaign/skills/<bucket-name>/SKILL.md` — Unfolded Reporting Sub-Skills (for deliverable buckets 1–3):**
   - Compile one self-contained `20–30` line skill per deliverable bucket so each writer starts from a tailored guide: (a) `(entry_domain × violated_law × repair_clarity)` criteria (using concrete law names: `UNCHANGED` frame law, safe-wrapper soundness, AST spine invariance under leaf substitution, `alpha`/`RepInv` equivalence), (b) repo verification commands—for repair buckets, confirming the test fails on its intended delivery base (`target_sha`, or `target_sha` plus declared `depends_on` repairs) and passes with the fix across the generalized property suite and `--release`; for reproduction-only tradeoff/ambiguity buckets, confirming the deterministic witness and contrastive baseline on `target_sha` (`or target_sha + depends_on`) alongside a concise comparison of candidate contracts—(c) repair depth and native repo test conventions, (d) witness-led precision (naming the tested API, treating `maintainer-confirmed` decisions as intended project behavior while framing `caller-expectation` items where public docs are silent as specification questions or integration tests, citing any inspected caller that changes the conclusion, and marking uninspected callers `unverified`), and (e) destination (`fix/<slug>` cut from `target_sha`—or stacked in `depends_on` order—vs. `.proptest-campaign/out/<bucket>/`).
3. **`.proptest-campaign/ledger.md` — Campaign State, Covered Transitions, & Discharged Obligations:**
   - Track pinned `target_sha`, modules modeled, worktrees, assigned laws checked (e.g., `alpha(step_impl(s, op)) == step_model(alpha(s), op)` for an exact state-machine model, or a one-sided cache/solution soundness relation, paired with `RepInv(s)`) with the exact operations covered and mutation-calibration status, **cross-module composition obligations** (`produce_fn`, `required_condition`, `consume_fn`, `resolution: open | "<function> establishes <condition> at <file:line> on <target_sha>" | violated_by(<test_name>)`), and divergences grouped into **root-cause equivalence classes** (`id`, `module`, `worker_base_sha`, `depends_on`, `repair_mode: patch | repro_only`, `violated_equation`, `caller_context: cited | unverified`, `test_name`, `status: candidate | verified | packaged | dropped`, `bucket`).

## 5. Role-scoped subagent orchestration and cross-module composition

Give each subagent a crisp, focused brief and the single skill file its role uses so every context starts fresh and unencumbered by prior search history. Because subagent harnesses do not auto-expand `$skill` sigils inside delegated prompts or scan `.proptest-campaign/skills/`, pass exact absolute `SKILL.md` file paths and ask each subagent to read its assigned skill file first (when running in a single context, walk these roles sequentially using `operating-model.md` and `ledger.md` as state):

1. **Specification Scout (`read-only`, runs once in Step 1):** digests repository docs, examples, manifests, and commit history into source-cited contract terms, then returns.
2. **Coordinator (this context — `$proptest-campaign` + `operating-model.md` + `ledger.md`):** selects high-leverage modules (`TODO`/`FIXME` hotspots, `Recent Feature × Older Consumer` pairs, coupled caches/planners), dispatches **Module Conformance Briefs**, sweeps sibling occurrences via `rg` in owned-repo mode, orders or folds `depends_on` findings before packaging, and turns worker assumptions and incidental observations into follow-up checks. Whenever Worker A records an open `produce -> consume` assumption, dispatch a composition check across supported inputs `x`: verify that `produce(x)` satisfies `consume`'s documented precondition and fulfills the promised relation between `x` and `consume(produce(x))` (such as `consume(produce(x)) == expected(x)` when unique, or solution-validity predicates like topological order when multiple outputs satisfy the contract; plus `obs(produce(x1)) == obs(produce(x2))` where `obs` promises representation-insensitivity), recording `"<function> establishes <condition> at <file:line> on <target_sha>"` in `ledger.md` or capturing the minimal `consume(produce(x))` counterexample. Whenever an observation falls outside a worker's assigned law, check whether a separately supported promise explains its relevance and issue a new brief for that promise.
3. **Model & Harness Workers (given `proptest-praxis/SKILL.md` + a concise `Module Conformance Brief`):** dispatch each worker with a structured brief whose fields keep attention directly on the module's algebra and execution harness:

   ```yaml
   target_sha: <pinned sha>
   module: <path and named API(s)>
   promises: <laws to check + citation @ file:line | maintainer-confirmed(id) | caller-expectation(id) | hypothesis>
   model_law: <alpha(step_impl(s, op)) == step_model(alpha(s), op) | cache/solution soundness relation + RepInv>
   preconditions: <documented caller/unsafe obligations to uphold>
   commands: <1-3s test target, --release, Miri/ASan, and bwrap/container confinement wrapper>
   ```

   While the worktree and build cache are warm, workers can immediately add checks for adjacent promises on the same module that code reading or testing brings into focus (such as multiset preservation alongside sort order) whenever repo evidence supports them. Workers return one structured `Worker Outcome` per module or root-cause class—giving clean calibrated modules, confirmed regressions, and open specification questions equally concrete completion shapes:

   ```yaml
   status: verified_clean | confirmed_divergence | open_question
   provenance: { target_sha, worker_base_sha, depends_on: [<id>], api, promise_source }
   coverage: { law_checked, ops_covered, calibration_break_caught }
   witness: <minimal #[test] or observed diagnostic + command & delivery-base/--release output>
   resolution: <verified candidate diff | candidate contract options | open question>
   leads: [<produce -> consume assumption or adjacent promise to check next>]
   ```

   When a failure or `Miri`/sanitizer diagnostic directly establishes a violation of a settled module promise, workers replay the minimal test on `target_sha` (recording `depends_on` when unmasked by an earlier `worker_base_sha` repair) and rerun `model_law` over `ops_covered` and `--release` before and after the candidate repair; when two defensible interpretations fit the docs or an observation points outside the assigned promise, workers return `status: open_question` with the observed witness and `leads` for the coordinator.
4. **Fresh-Eyes Reviewer (`read-only`, fresh context — ideally on a second model family):** hand a fresh source-level `read-only` agent a self-contained review packet: `target_sha`, `worker_base_sha`, `depends_on` (plus any prerequisite diff), the assigned law, candidate test, captured delivery-base/`--release` output, covered-operations list, candidate diff or contract-option summary, module source at `target_sha`, and the exact promise evidence (`doc/example/comment @ file:line`, `maintainer-confirmed (<decision-id>)`, or `caller-expectation (<decision-id>)`). Read repository citations directly to test whether a competing interpretation fits, and distinguish a `maintainer-confirmed` project decision from a downstream `caller-expectation` when public docs are silent; confirm repair-mode tests fail pre-fix on their intended delivery base, satisfy the assigned law over the recorded operations post-fix, and keep the witness minimal in LOC. Name the tested API, citing any inspected caller that changes the conclusion and marking uninspected callers `unverified`.
5. **Bucket Writer (given `<primary-root>/.proptest-campaign/skills/<bucket>/SKILL.md` + the verified review packet):** uses the unfolded bucket sub-skill to produce a clean `target_sha`-based branch (folding co-dependent repairs or stacking them in `depends_on` order) or a concise staged writeup.
