# Property-testing campaigns: staging and role-scoped specialization

Every repository has an implicit operating model: which functions promise total behavior over arbitrary inputs versus caller-established preconditions, whether you are contributing surgical external patches or tightening types in a codebase you own, and how findings route across pull requests, design questions, or maintainer channels.

Treat campaign setup as **Futamura staging and partial evaluation (`discover_repo >>= (\repo_model -> specialize(workflow, repo_model))`)**: recover that operating model once at the target commit, compile lean role-scoped sub-skills onto disk, and hand each subagent only the skill and brief its task requires. Start the coordinator with this skill; load [`write-reports`](../write-reports/SKILL.md) (and [`root-and-branch`](../root-and-branch/SKILL.md) for owned repositories) when unfolding sub-skills in Step 3, and pass [`proptest-praxis`](../proptest-praxis/SKILL.md) by file path to module workers.

## 1. Isolate the workspace and scout the repository

Pin the target commit (`target_sha`) up front and run the campaign in a disposable external workspace—such as `git clone --shared <repo> /tmp/<repo>-campaign/work` with campaign files under `/tmp/<repo>-campaign/state/`—so parallel worktrees, runner logs, regression seeds, and retained reports never touch the developer's working checkout.

Spawn a short-lived, read-only **Specification Scout** subagent (when subagents are available) at `target_sha` to return a source-cited summary:

- **Promises, preconditions, and deliverable paths:** inspect `README`, `CONTRIBUTING.md`, `SECURITY.md`, `AGENTS.md` / `CLAUDE.md`, public examples, and issue/PR templates. Map selected entry points, accepted inputs, documented caller obligations, and promised behavior—citing the exact source (`doc`, `example`, `test`, or `comment @ file:line`) for each claim rather than compressing hints into axioms—alongside test conventions and `CONTRIBUTING.md` / `SECURITY.md` routing rules.
- **Architecture and fast compile loops:** inspect manifests (`Cargo.toml`, `package.json`, `*.gemspec`, `pyproject.toml`), CI configs, test runners (`cargo nextest`, `pytest`, `rake`), feature flags, and `unsafe` or C/FFI boundaries. Identify leaf crates with `1–3s` incremental builds versus heavy binaries where narrow pocket test targets keep iteration fast, plus core data structures, planners, parsers, and cross-module `produce -> consume` pipelines.
- **Uncertainty markers, reactive point-fixes, and recent features:** sample existing property tests, grep for maintainer uncertainty comments (`TODO`, `FIXME`, `HACK`, `workaround`, `subtle`), and check `git log` for **recent reactive point-fixes** (hotfixes, release-blocker patches, security fixes, crash band-aids—which often introduce adjacent regressions or update only one side of a coupled invariant) and **recently landed features/modes** meeting older caches, visitors, and serializers.

## 2. Clarify high-value boundaries with the user

Present a compact table of inferred defaults, then filter by **value of information**: ask only the `2–4` unresolved questions whose answers change API obligations, repair depth, or deliverable routing so the user can approve defaults in one reply. When running unattended, record inferred assumptions explicitly as hypotheses.

- **Input domains and caller obligations:** separate documented preconditions (`C caller must pass valid pointer`, `compile-time literal only`) from incidental habits of current outer callers (`current caller happens to pass a fresh copy`), and cite the source for each promised law (`Ok`/`Err` totality, `UNCHANGED` outside a workspace directory, safe-wrapper soundness, or explicit resource bounds where promised).
- **Ownership mode and speaker authority:** confirm whether this is an *external contribution* (minimal surgical fixes) or an *owned repository* (where [`root-and-branch`](../root-and-branch/SKILL.md) concept culling and `|Type| == |ValidStates|` tightening are welcome), and note whether user-supplied expectations come from an API owner or a downstream caller.
- **Deliverable buckets:** confirm active destinations—such as (1) *Correctness or root-fix PR*, (2) *Design / specification question* (reproduction-only test + options when docs are silent or fixing alters public semantics, layout, or complexity), (3) *Private maintainer report* (written to `<campaign-dir>/out/` per `SECURITY.md`), and (4) *Ledger drop*—plus parallel worktree and `Miri`/`ASan` budget.

## 3. Unfold repo-specific sub-skills to disk

Specialize [`write-reports`](../write-reports/SKILL.md) (and [`root-and-branch`](../root-and-branch/SKILL.md) in owned-repo mode) once into compact files under `<campaign-dir>/state/`:

1. **`operating-model.md`:** pinned `target_sha`, source-cited API promises and caller preconditions (including verbatim user decisions tagged as API-owner vs. caller expectation), non-goals, routing table, and fast test / `--release` / `Miri` / `ASan` / `bwrap` recipes. When several target modules share one core IR, schema, or AST, also write a short `domain-fixtures.md` capturing the shared miniature valid-AST generator and in-repo differential pairs once for all workers.
2. **`skills/<bucket>/SKILL.md`:** one self-contained `20–30` line reporting skill per active deliverable bucket stating admission criteria, baseline/fix verification commands, repair depth, caller-context honesty, and output destination (`clean branch off target_sha` vs. `<campaign-dir>/out/<bucket>/`).
3. **`ledger.md`:** modules and laws covered, cleared guards (`file:line` notes explaining why an inspected guard held so workers skip cleared paths), **Rely–Guarantee** `produce -> consume` assumptions (`open`, discharged by `<function> at <file:line>`, or violated), and confirmed divergences grouped into root-cause equivalence classes.

## 4. Orchestrate role-scoped subagents

Pass explicit `SKILL.md` file paths when delegating (since subagent prompts do not auto-expand `$skill` sigils), giving each role a fresh context free of prior search history:

1. **Coordinator (`proptest-campaign` + `operating-model.md` + `ledger.md`):** prioritizes modules (`reactive point-fix neighborhoods`, `Recent Feature × Older Consumer` pairs, `TODO`/`FIXME` hotspots, coupled caches/planners) and dispatches per-worktree workers. When a worker surfaces an open `produce -> consume` assumption (*"`produce` omits `X`, assuming `consume` enforces `X`"*), dispatches a targeted check verifying across supported inputs `x` that `produce(x)` satisfies `consume`'s precondition and the promised input-output relation. When an observation points to a supported promise outside a worker's brief, issues a follow-up brief.
2. **Module Workers (`proptest-praxis/SKILL.md` + a `10–15` line Module Brief):** give each worker its worktree, `target_sha`, target module and APIs, cited promises, candidate model or soundness law, caller preconditions, fast test command, and conditional checks (`--release`, `Miri` for `unsafe`, `ASan`/`UBSan` for C/FFI, `bwrap`/container confinement for mutating path tests). While the worktree and build cache are warm, workers also check adjacent promises on the same module that code reading or testing brings into focus. Clean runs return the laws and operations covered plus the mutation-calibration check caught; confirmed bugs return the minimal test, decisive test command and output, candidate repair, and open leads; unsettled contracts return a characterization test and the competing interpretations.
3. **Fresh-Eyes Reviewer (`read-only`, N-version check — ideally on a second model family):** give a fresh `read-only` agent on a distinct model lineage the candidate test, decisive command and output, optional diff or options, module source at `target_sha`, and the exact cited source (or verbatim user quote) for the promise. Read primary citations directly to test competing interpretations, check witness minimality and `--release` / invariant coverage across sibling paths, name the tested API, and cite any inspected caller that changes the conclusion while marking uninspected callers `unverified`.
4. **Bucket Writer (`<campaign-dir>/state/skills/<bucket>/SKILL.md` + verified packet):** for repair buckets, cuts a clean branch from `target_sha` (stacking dependent fixes explicitly when an earlier fix unmasks a second bug) and runs the decisive test command before and after the fix (plus `--release`) to confirm the branch is self-contained; for specification questions, tradeoffs, or private maintainer reports, replays the witness on `target_sha` and writes the standalone artifact to `<campaign-dir>/out/<bucket>/`.
