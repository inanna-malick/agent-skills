# Write Reports

A great technical report has the clarity of a four-line mathematical counterexample: a maintainer who has never seen your exploration transcript, generator, or reference model can run or trace the minimal case in seconds, see the exact contract or invariant that disagreed, and make a concrete engineering decision.

Select and combine the lenses below as the audience, venue, and topic require.

**Decision space; audience design; inline literal counterexamples.** Identify who reads the artifact and what choice it supports: merging a clean bugfix patch, weighing a semantic or performance tradeoff, answering a specification question, or scoping a backlog issue. Lead immediately with the concrete function, **exact literal input** (`{"a":1,"A":2}` rather than abstract prose like *"an object with two keys differing in case"*), observed output, expected output, and inline `10–25` line standalone regression test so a maintainer never has to reconstruct the example from external driver scripts. Use flat, plain-prose report and PR titles stating the component and broken invariant (`SelectionMap: equal values produce different hashes`, `decode_frame: cursor index advances past slice length on multi-frame input`) paired with neutral test names (`selection_map_equal_values_hash_differently`), never echoing raw diagnostic-tool banners, and re-project internal model notation (`alpha`, `RepInv`, uninterpreted sort names, discovery branches) back into the repository's native domain vocabulary.

**Counterexample compression; `Δ = 1` baseline pairs; greenfield tests.** Strip away every incidental operation and parameter until only the minimal deterministic failing case (`ddmin` fixed point) against the base commit remains (`10, 11` then reopen and append `13` reading back `10, 11, 12`; `abcd` in Replace mode recovering `Xabcd` instead of `Xbcd`), written fresh from scratch **at the exact API boundary whose contract was established** (public entry point for external promises, or native module test boundary for internal invariants) so discovery-branch models and helper imports stay behind. When a passing case exists, pair the failing case with a nearby **passing baseline** running on an independent fresh instance across identical APIs while varying **one parameter (`Δ = 1`)**—unchunked vs. chunked on the same bytes, fresh vs. warmed cache on the same keys—asserting both cases in the same test.

**Multi-process integration cases; build metadata.** When a bug crosses process, service, or database boundaries beyond an in-process unit test, package a minimal `compose.yaml` using unmodified upstream images and a short stdlib driver script, stripping away custom helper wrappers. Record the exact base commit SHA (plus any prerequisite fix commit when an earlier bug masked a second case), build profile (`debug` vs. `--release`), feature flags, standard CI checks (`Miri`, `ASan`, `UBSan`, `-race`), exact source constants verified against that commit, and runnable test command.

**Scope claims to the test; caller contracts vs. caller habits.** Match every claim to the exact scope of what the test executes and verifies: the named API whose contract the test exercises, input domain, documented caller obligations, minimal executable regression test, observed vs. expected behavior, verified CI build flags, and proposed fix (when the contract determines one). Distinguish a documented caller precondition (`Rely` obligation) from an incidental habit of current outer callers: if an inspected caller passes a fresh copy, normalizes upstream, or avoids the sequence, cite it plainly; otherwise mark uninspected caller behavior `unverified` and let the minimal executable unit test carry the weight of the claim.

**One invariant per patch; root-cause grouping; atomic changes.** Group failing cases by underlying representation invariant and repair boundary rather than by surface symptom or call site. Collapse multiple traces resolved by restoring one invariant into a single patch or report; keep independent mechanisms separate so each change can be reviewed, merged, or reverted cleanly.

**Contract bugs vs. design questions; cross-model review.** Distinguish clear contract bugs from undocumented corner cases, asymptotic complexity cliffs, or intentional simplifications. Before finalizing a report, review the test and patch skeptically—across a second model family when available—against documentation, explicit caller preconditions, existing tests, and `--release` behavior, iterating until the unit test is self-contained and minimal in lines of code. Frame genuine ambiguity as a concise specification question, and update or withdraw claims plainly when maintainer context changes the picture.

**Repair ownership; surgical patches, root-type fixes, and test-only notes.** Match the proposed action to repository ownership and maintainer latitude, sampling recent maintainer commits to match the project's native code and test style. For external repositories, supply the smallest complete, idiomatic fix (`Red -> Green`) when the contract is clear, noting briefly why the change restores the invariant across sibling call sites without regressing fast paths or valid callers (and when an investigation happens to answer an adjacent `TODO` question in the source, include that concrete answer as a small bonus note). For team-owned repositories, note when sibling failures warrant culling duplicate wrappers or tightening a shared carrier type (`|Type| == |ValidStates|`) across call sites rather than adding point guards. Supply a standalone regression or characterization test and a concise comparison of candidate options when changing behavior affects public semantics, memory layout, asymptotic complexity, or module boundaries that maintainers should weigh deliberately.

**Contributor etiquette; project conventions; local staging.** Match format, detail, and output bucket (`out/pr/`, `out/discussion/`, `out/maintainer/`) to the project's `CONTRIBUTING.md` guide, issue/PR templates, and documented maintainer conventions, staging all artifacts locally so the developer controls any upstream submission.
